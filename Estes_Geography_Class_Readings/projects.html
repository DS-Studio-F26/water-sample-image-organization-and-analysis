Final Projects

The following is an overview of expectations for delivering the final project.

Set-up

Work with your team to set up a single private repo on the agroimpacts GitHub organization or one of your personal profiles. One of you can set it up, and then add the rest of you as contributors. Name the repo so that it describes the project, and is all in lowercase with no underscores. Short is better.

Key components

Project description

Make a folder in your repo called “notebooks”, and within save a single colab notebook named description.ipynb. The notebook should contain the following sections.

  1. Summary: A brief (up to 250 words) description of the project and its objectives (10 points).
  2. Division of labor: A description of who did what on the project (5 points).
  3. Key findings: A very short summary of key findings (5 points).

Commit the notebook in the repo when you are done with it in colab. You may also wish to do this locally in jupyter notebook/jupyter lab. This notebook is basically an abstract.

Primary analyses

Your final project is built in the same repository, following the steps outlined in description.iypnb.

Each sub-team in the final project group should have a notebook that lays out the analysis undertaken by the sub-team. For example, in the drone image labeling project, the team developing the cranberry models could have a notebook called prithvi-finetuning-smallsample.ipynb, and the group working on cropland mapping with the Lacuna Fund labels could have a notebook called resunet-train-mostaccurate.ipynb.

Final notebooks should have the following structure:

  1. Introduction: A brief summary of your sub-team’s project objectives (<250 words).
  2. Methods: A summary of the approach used to attain the objectives. E.g. what data you use, how did you process it, what model did you use, and how did you adapt it. This section should be brief but informative. Provide references to code used, etc.
  3. Results/analysis: A brief description of the results, interleaved with any analytical steps. For instance, show:
    • Your model training/fine-tuning loop.
    • You evaluation metrics
    • Prediction code and predictions results (tiles/chips resulting from the prediction step)
  4. Discussion: A brief summary of main findings, any difficulties or surprises encountered, and what improvements could be made.

Each sub-team/contributor should have a notebook that aligns with this structure. If there is a compelling reason to have a different structure, please let us know and we can come to an arrangement.

Note, mark clearly who authored the notebook. If two people are working on the same notebook, please place initials for who did what on that notebook.

Repo and code organization

It is acceptable to have all code needed to undertake the sub-team/team project in the relevant notebook, including model code, etc. In this case, we would expect to see the repo organized as reponame with one sub-folder named notebooks, with the required notebooks (including the original .ipynb) in the folder. The structure will look something like this:

.
└── reponame/
    ├── README.md
    └── notebooks/
        ├── description.ipynb
        ├── subteam-1.ipynb (named descriptively)
        └── subteam-2.ipynb (named descriptively)

The README should have the project name/brief description of the project, the names of the contributors, and a link to description.ipynb.

It may also be preferable for large blocks of reusable code to go into .py files that are loaded as modules from your repo. In this case, the structure would like more like this:

.
└── reponame/
    ├── README.md
    ├── notebooks/
    │   ├── plan.ipynb
    │   ├── subteam-1.ipynb (named descriptively)
    │   └── subteam-2.ipynb (named descriptively)
    └── reponame/
        ├── __init__.py
        ├── code1.py (e.g. unet.py)
        └── code2.py (e.g. dataloader.py)

For example, the model architecture, data loader, etc, can all go into a sub-folder in your repo named the same as the repo main folder (note: see the naming convention for the repo above). If you have an __init__.py file in the folder, then the modules can be imported into your notebooks and used there. In colab, you can clone and read in your repository by placing code such as the following in our notebooks (this example is for cloning `fieldmapper, or for pulling the latest commits into an already existing clone of `deeplearner`):

# Clone github repository setup

        !git branch

Exceptions

  • We realize that time is short and some projects are more experimental than others. For example, we know that difficulties might prevent some projects from getting prediction outputs, or even a fully trained model. We will factor that into assessment.

Assessment

The final project will be assessed out of 70 points. 20 of the points are already allocated to the description (this is basically automatic if it conforms to what is asked). For the remaining 50 points, each sub-team/contributor will be assessed separately for their individual notebooks. We will assess effort based on a combination of git commit histories, as well as documentation of effort in the form of initials added to sections within notebooks or other repo files (e.g. .py).

Points will be assigned as follows:

  • Quality of notebook (20 points). Does the team/sub-team notebook conform to the specifications set out above, and is the writing, code, and figures clear?

    • An extra 2.5 points will be awarded to teams that import their main code into analytical steps, rather than rely on all code compiled in notebook cells.

  • Quality of results (20 points): Did the team demonstrate good progress, sound results, and analysis. I.e. did they get their inputs formatted correctly, ingested into the model, train and evaluate a model, and demonstrate a prediction?

    • As mentioned above, the ability to achieve all these ingredients will vary between groups and teams, so we will factor those differences into our assessments under this category.

    • If a group can’t get all the way though model training and prediction, we will evaluate the degree of team progress given project difficulty. Did the team do the best job they could to get as far as they could? Did they try several approaches to overcome problems? Did they adequately document bottlenecks and difficulties? Did they wrap up the project at a point from which further efforts could be readily taken up after submission?

  • Quality of discussion (10 points): This will assess the quality of insights provided by the team into their results. Does the teams assessment of results against expectations demonstrate understanding of the model, workflow, and analysis. Does the discussion explain likely reasons for bottlenecks/difficulties/unusual or unexpected findings?
